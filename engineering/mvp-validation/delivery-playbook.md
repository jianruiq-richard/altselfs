# 从许愿到首轮付费验证

本流程依赖已实现并测试的轻量 starter。本目录目前只给出规范；首次建设 starter、开通收款账户和搭建发布设施的时间须单独计算。

## 1 先写一页产品契约

从 [契约样例](product-contract.example.json) 复制为项目自己的 `product-contract.json`，只确定：

- 谁在什么场景下，需要什么具体结果。
- 用户从进入页面到拿到结果，只经过哪一条核心流程。
- 哪一步收费、售价多少、交付什么、失败如何处理。
- 首批用户从哪里来、观察多久、看到什么证据才继续或调整。
- 哪些依赖已可用、成本上限是多少、哪些扩展模块确实必要。

能推断的直接填默认值。收款主体、外部服务授权和产品承诺等不能推断的事项留为待落实；不因此阻塞与其无关的预览工作。金额和验证门槛是待检验的实验设置，不是行业通用标准。

样例中的 `null` 表示尚未配置，不是可跳过。真实收费前需填写适用的价格映射、资源与商户归属、管理员、数据保留和退款政策、失败处理期限、支持与告警、对账责任和频率、预算与限流；明确不启用的可选服务可保持为空。

## 2 先交付能理解的预览

实例化固定版本，生成首页、一个业务流程和后台。默认托管子域名，复用 UI 与认证控件；独特界面留给核心结果展示。

预览应能跑通已实现的真实核心逻辑；示例结果或尚未连接的依赖明确标示。测试支付、体验额度和生命周期对创作者可见。无真实收费能力时，不显示为可对公众收款的成品。

十分钟只可作为已有模板覆盖范围内的预览实验目标。端到端计时要分别记录模板准备、生成、人工补充、测试、发布和账户等待时间，不能把可点击预览当成全部上线耗时。

## 3 打开真实支付前完成五项验收

| 门槛 | 最低证据 |
| --- | --- |
| `M1` 真实价值 | 干净构建；真实浏览器完成核心流程；刷新后结果仍在；错误可恢复；服务端禁止未购买读取付费结果 |
| `M2` 身份与隔离 | 两个普通用户与管理员验证；跨用户读取/修改失败；越权后台访问失败；密钥不进客户端 |
| `M3` 支付与交付 | 测试支付成功、取消、失败、适用的延迟支付；并发重复与乱序回调；数据库失败后恢复；退款/争议不会重新开放结果；订单、授权与交付一致 |
| `M4` 托管与容量 | 部署版本和环境可追溯；100 用户容量证据；限额与暂停开关；备份恢复、回滚和告警；启用的可选模块补测 |
| `M5` 上线与测量 | 生产 URL 的真实流程；经营主体授权的 live 小额支付与对应交付/退款记录；漏斗去重及测试流量排除；渠道归因；条款、支持联系人、失败处理与预算已配置 |

这是验收内容的合并，不是只检查五个页面。底座的鉴权、支付和恢复用例随模板版本维护；每个产品仍执行自己的核心浏览器流程、数据权限、价格映射、交付和生产检查。所有环境和测试模式单独记录。

在 `M5` 完成前，只对授权测试人员开放 live 验证；全部通过后才开放公众付费。任何实际扣费、退款或对外发消息，都应处在该执行任务的授权范围内。本规范本身不触发这些操作。

收款账户资格、结算信息或第三方授权未完成时，可以交付预览并列出阻塞项；不能标为已完成付费上线。订阅、文件、任务或人工交付的验收须与实际承诺相符。

## 4 技术状态与市场结论分别记录

从 [证据样例](validation-evidence.example.json) 复制为项目自己的 `validation-evidence.json`。每项证据记录环境、版本、执行时间、结果和可核验记录，禁止把示例空值变成默认通过。

| 状态 | 含义 |
| --- | --- |
| `not_started` | 尚未创建可运行预览；本目录的空白证据样例处于此状态 |
| `preview` | 可体验；未完成真实收款与生产验收 |
| `production_unverified` | 已部署到生产环境，仍有门槛未通过；公众付费入口保持关闭 |
| `production_verified` | `M1` 至 `M5` 全部通过，容量承诺与实际证据一致，可开放公众付费 |

市场结论另用 `not_started`、`collecting`、`inconclusive`、`supports_hypothesis` 或 `does_not_support_hypothesis`。技术上线状态不推出市场结论。一次购买支持的是这次报价和交付的吸引力，不自动证明续费、规模化获客或长期留存。

## 5 最小获客与验证闭环

创作者选一个渠道，得到带来源参数的链接和首发素材；确认实际发布或投放后再观察。模板不承诺自动获得用户，也不默认代用户发帖、发邮件或买广告。

上线前写明观察窗口、有效样本定义和继续/调整规则。例：七天内通过一个相关社区获取首批访客，记录陌生用户是否按标价购买、是否拿到结果、是否认可价值；具体样本和付费门槛由产品假设决定。流量不足时继续获取样本，结论为证据不足。

检查漏斗的用途是决定下一步：

- 有相关访问却没人开始：检查人群、价值表达、示例和入口。
- 有尝试却没人购买：结合反馈检查结果价值、信任和报价。
- 有付款却交付失败：先修复交付，再继续验证需求。
- 有付款和交付但集中退款：检查承诺与真实价值是否一致。
- 少量陌生用户付费且认可结果：支持这一小范围假设，再验证重复获客或复购。

这些是排查方向，不是仅凭转化率就能确定的原因。看板同时显示计数、分母、时间窗口和来源；不只显示百分比或“验证成功”徽章。

## 6 每次交付与升级

交付包保持一页：预览/生产地址、管理员入口、一个核心流程说明、技术状态及证据、首发链接和素材、已知依赖、预算及暂停方法、故障联系人、下一轮要验证的问题。另附代码版本和恢复入口，源码与运行资源的归属明确。

只有出现业务触发条件才增加能力：处理经常超过短请求限制时加任务；需要真实文件时加存储；要验证持续收费时加订阅；实际多人协作时加组织权限。引用 [完整架构](../paid-mvp/architecture.md) 的对应部分，避免每次从轻量版重新堆出整套平台。

衡量模板效果用真实数据：从愿望到预览/付费上线的时间、生成成本、人工介入次数、验收失败原因、单次交付成本、首个陌生付费用户的来源与时间。当前这些指标尚未测量。

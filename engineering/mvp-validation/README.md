# 付费 MVP 验证模板 · 轻量版

目标：把一个想法变成可访问、可使用、可收款的小产品，让创作者尽快知道**哪类用户愿意为什么结果付费**。

本目录是独立的架构与模块模板，保留 [完整工程标准](../paid-mvp/README.md) 不变。海外优先，复用现有 Next.js、Clerk、PostgreSQL、Stripe 和托管方式。适用日期：2026-10-18。

**当前交付是设计规范和填写样例，尚不是可运行 starter、一键生成器或已部署产品。** JSON 不是现有程序支持的配置格式；示例中的支付、容量和市场验证均未执行。

## 默认产品形态

**一个人群、一个核心结果、一个收费方案、一个首发渠道、一轮验证。**

| 组成 | 轻量默认值 |
| --- | --- |
| 三个主要界面 | 首页含定价与示例；工作页完成核心流程；后台查看验证结果 |
| 用户系统 | 托管登录，邮箱或 Google 选一种；先体验，保存私人数据或购买时登录 |
| 业务 | 一个核心对象，一条输入到结果的路径 |
| 支付 | 一次性购买一个结果，Stripe 托管 Checkout |
| 后台 | 漏斗、订单与交付状态、失败记录、反馈、Stripe 订单链接 |
| 运行 | 一个 Next.js 应用承载页面和短 API，托管 PostgreSQL 存数据 |
| 发布 | 先用托管子域名，复用部署流水线；自定义域名后加 |
| 容量 | 付费正式版目标仍为 100 个活跃在线用户，必须提供测试证据 |

隐私、条款和联系入口继续保留为小型标准页面。“三个主要界面”不限制必要的回调、登录或法律页面。

## 四个模块

| 模块 | 必须交付 | 默认不生成 |
| --- | --- | --- |
| `core` 核心价值 | 价值说明、输入、真实处理、结果和必要历史 | 多工作区、多业务线、通用 agent |
| `identity-data` 身份与数据 | 托管登录、服务端身份校验、数据归属与隔离 | 团队、组织、多层角色、自建账号系统 |
| `purchase-delivery` 购买与交付 | 单一报价、真实支付确认、幂等交付、退款状态 | 积分钱包、套餐矩阵、优惠券系统、默认订阅 |
| `validation` 验证后台 | 渠道到交付的漏斗、真实订单、反馈和成本记录 | 通用 BI、复杂 CRM、自动投广告或自动发帖 |

部署、日志、限额、备份和基本安全由共同底座承担，不随每个产品重新生成一套系统。模块合并只减少接口和页面数量，不取消支付一致性和数据隔离。

## 与完整架构的关系

| 完整架构中的能力 | 轻量版处理方式 |
| --- | --- |
| 独立定价、设置和管理页面 | 定价并入首页，账号入口并入工作页，后台仅一页 |
| 通用权益系统 | 单次购买直接关联核心结果；需要订阅或额度时再升级 |
| 持久任务 worker | 短流程默认省去；长任务、重试或可靠异步交付时必须加入 |
| 文件资产与对象存储 | 文本和 JSON 直接入库，打印由浏览器完成；真实文件需求再接 OSS |
| 独立运营系统 | Stripe Dashboard 处理低频退款，后台展示状态和处理入口 |
| 每个产品的基础设施 | 复用托管设施与发布流程，项目数据库、权限和密钥仍隔离 |
| 多个收费与增长模块 | 一种主报价、一条带来源参数的分享链接、一份首发素材 |

适合个人工具、小型生成器、付费报告、轻量表单和简单服务验证。报告若依赖长时间抓取或 AI，须增加任务模块。双边市场、团队工作流、复杂订阅和多阶段 agent 产品直接参考完整架构，不强行压进这个默认形态。

## 文件与使用顺序

1. [architecture.md](architecture.md)：模块、数据、支付、运行边界及升级条件。
2. [product-contract.example.json](product-contract.example.json)：把许愿收敛为最小产品和验证实验。
3. [delivery-playbook.md](delivery-playbook.md)：从预览到收款、验收和首轮验证的执行顺序。
4. [validation-evidence.example.json](validation-evidence.example.json)：分别记录技术就绪证据和市场证据。

示例选择不需要 AI、上传和 worker 的报价单工具，用来说明最轻的可用结构。可替换业务模块，不能把示例需求、价格或验证门槛当成已验证市场结论。

## 可复用任务指令

> 按 engineering/mvp-validation 的轻量模板，把我的想法做成可验证付费需求的海外 Web MVP。先确定目标用户、一个核心结果、一种报价和首轮验证方法；能从描述推断的采用默认值。保留用户系统、真实支付、数据隔离和验证后台，按实际业务需要添加任务、文件或订阅模块。交付可访问地址、管理员入口、真实流程和容量证据、成本上限及首发素材。区分预览、技术验收通过和市场验证结果；未实现或未测试的能力不得标为完成。

使用上述指令前，需要先把本目录实现为经过验证的 starter。速度来自减少每次生成的业务量和复用已验证模块；本目录不承诺任意想法十分钟上线，也没有测得实际单项目成本。

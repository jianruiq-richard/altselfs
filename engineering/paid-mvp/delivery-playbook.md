# 从产品想法到付费上线的交付方法

把用户的自然语言描述转换成可测试的产品契约，然后复用经过验证的底座完成一条付费闭环。约 4 至 8 小时是简单业务在底座、账号和支付条件齐备后的交付目标，不能作为任意产品复杂度的保证。

## 1 先完成一次底座建设

第一次不能同时把“抽取框架”和“几小时生成业务”视为已经完成。建议按以下顺序建设独立 starter，每项通过后再进入下一项：

1. 抽取身份、个人数据作用域、应用壳和管理员权限；建立空数据库迁移及测试用户。
2. 抽取 Stripe 购买意图、inbox、订单、权益和管理界面；通过并发重放、失败恢复和退款测试。
3. 抽取 Job、租约、幂等、对账、outbox；把跨库默认设计收敛到一个产品数据库。
4. 固定 Vercel、容器 worker、数据库、对象存储的资源模板；实现 preview、生产发布和回滚。
5. 建立一个可丢弃的示例产品，完成浏览器、容量、权限、支付及恢复验收，发布 starter 版本。

规划上可先预留数个工程日完成这次抽取和加固，实际以门槛通过为准。以当前代码状态，直接复制整仓后宣称已获得通用底座会把历史业务和未验证边界一并带入。

## 2 把许愿转成产品契约

用户通常只需要提供：谁会用、想解决什么、最终拿到什么。系统补全页面、数据、错误处理和基础设施。仅对会改变核心价值、收费责任或关键外部依赖的问题提问，一次最多三个。

| 从自然语言提取 | 契约中的明确表达 |
| --- | --- |
| “给独立开发者分析一个网站” | 用户身份、URL 输入、分析对象与范围 |
| “告诉他值不值得做” | 具体结果字段、依据和缺数据时的表达；不承诺无法验证的准确性 |
| “能收费” | 付费时机、商品、金额、币种、付款后得到什么 |
| “带后台” | 用户、订单、履约状态、退款和失败重试 |
| “能上线” | 资源所有者、域名、生产环境、告警、维护入口 |
| “100 人能用” | 在线负载、API 指标、执行槽、队列容量及超载行为 |

契约 MUST 同时包含：主流程、显式不做项、默认假设、数据归属、付费点、失败退款规则、外部依赖、容量、成本上限、验收场景。页面数量不是需求完成度，用户得到结果才是。

不要要求用户选择数据库、队列库、组件库和部署命令。仅在现有默认栈无法满足已知约束时调整，并说明代价。

## 3 几小时交付的前置条件

开始计时前检查这些资源是否可用：

- 一个已验收的 starter 版本；目标业务能用现有模块表达。
- 代码仓库和 Vercel 部署权限，容器镜像和 worker 托管入口。
- 已就绪的托管数据库及备份设置；需要文件时有独立桶或产品前缀权限。
- Clerk 生产实例、回调域名和可用的登录方式。
- 目标经营主体有可收款的 Stripe 账号、结算条件和 live 配置；仅有 test key 不等于可付费上线。
- AI 或其他外部服务有合适的可用接口、配额及预算，不能依赖刚刚申请、等待审核的访问权。
- 管理员身份、支持联系方式、域名/DNS 权限。自定义域名传播未完成时可交付经过配置和验证的托管域名。

资源未满足时继续完成不依赖它的代码、预览和测试，明确把发布状态标为 `preview` 或 `production_unverified`。商户开户、OAuth 审核、供应商开通及 DNS 等待时间不属于代码生成可消除的时间。

## 4 每个产品的执行顺序

| 阶段 | 参考时间 | 必须产出 |
| --- | --- | --- |
| 产品契约与资源检查 | 0 至 30 分钟 | 确定输入输出、收费点、容量、默认项及缺失资源 |
| 初始化与 preview | 30 至 60 分钟 | 固定版本模板、独立环境、登录及空业务可访问 |
| 第一条业务纵向流程 | 1 至 2.5 小时 | 输入 → 存储 → 执行 → 结果 → 历史；含失败反馈 |
| 支付与后台连接 | 2.5 至 4 小时 | Checkout → webhook → 权益 → 履约；运营能定位和纠错 |
| 验收与修复 | 4 至 6 小时 | 权限、支付、恢复、移动端和目标负载的证据 |
| 生产发布与核验 | 6 至 8 小时 | 生产 URL、版本、真实闭环、告警、回滚和交付说明 |

时间可按复杂度压缩，门槛不能省略。每一阶段都维持一个能打开的部署版本；先让窄流程真实可用，再完善外观和辅助功能。

## 5 按需加入模块

| 用户想法 | 需要的增量 | 第一版先不加入 |
| --- | --- | --- |
| 目录、会员内容、轻量 CRUD | 核心表和权限、一次购买或订阅权益 | AI agent、复杂队列调度、浏览器 |
| AI 生成器、报告和文件转换 | 任务、限额、文件、失败重试、结果历史 | 通用代码沙箱、长期记忆、多代理 |
| 持续监控服务 | 调度、去重、通知投递、时区、停用 | 多种渠道、复杂工作流编辑器 |
| 团队工具 | Workspace、Membership、角色矩阵 | 未被要求的席位结算和企业 SSO |
| 平台代他人收款、市场撮合 | 独立的支付主体、分账与入驻方案 | 不可当作普通 Checkout 模板直接承诺 |
| 需要真人登录的网页自动化 | 独立浏览器池、账号恢复、任务容量和人工介入 | 不可按普通 Web 请求容量计算 |

## 6 强制验收清单

所有自动化应针对实际不变量和用户流程。不要通过“函数返回了预期字符串”替代数据库并发测试，也不要只检查页面不是 500。

| 门槛 | 验证步骤 | 通过证据 |
| --- | --- | --- |
| G1 可重建 | 干净 checkout，锁文件安装，类型检查、lint、生产构建；空库及上一版库迁移 | 命令、版本、退出码、迁移记录 |
| G2 身份 | 新用户注册、登录、退出、重新登录；草稿恢复；禁用用户被拒绝 | 浏览器结果、测试身份及时间 |
| G3 数据隔离 | 两个账号交换业务对象、文件、Job、Payment id；普通账号调用 admin | 预期拒绝且无数据泄漏或变更 |
| G4 核心价值 | 用户给真实输入，得到可消费的结果；刷新后保留 | 任务 id、结果引用、无演示兜底 |
| G5 支付履约 | Sandbox 完整支付、失败、延迟支付、取消；并发/重复/乱序回调；退款和适用的订阅流程 | Stripe 对象 id、订单、权益和履约状态一致 |
| G6 异步恢复 | 入队后断开浏览器、终止 worker、模拟供应商超时、重放提交、取消竞争 | 无重复经济副作用、无永久卡单；恢复状态符合契约 |
| G7 容量 | 执行 architecture 中的 100 VU、固定 RPS、入队峰值场景 | 测试脚本版本、资源规格、数据量、指标原始输出 |
| G8 运营 | 管理员查看错误、退款、禁用或纠正权益；普通用户不能操作 | 操作前后状态、audit id |
| G9 发布恢复 | 镜像/部署版本固定，readiness、流量切换、旧 worker drain、回滚；恢复备份到隔离库 | deployment id、digest、恢复及回滚结果 |
| G10 生产核验 | 托管域名 HTTPS、新身份登录、真实核心动作；经授权完成受控 live 购买及核对 | URL、时间、订单/权益/结果及告警验证 |

支付测试可以使用 Sandbox；“真实收款已验证”需要 live 证据。涉及实际资金的验收遵循事先约定的操作人和金额；没有证据时仍可交付已配置生产环境，但 paid validation 必须标为未验证，不能写完成。

压测放在隔离环境，不用未知上限的生产服务，也不对真实供应商执行 100 次付费调用。供应商真实流程另行小样本验证。单元测试、桩测试、Sandbox 支付和 live 验证分别记录，不混为一项全通过。

## 7 发布流水线要求

以下为待在 starter 实现的步骤约定，并非本仓库已有命令：

`preflight → install → lint/typecheck → unit → database integration → build → staging migrate/deploy → browser/payment/load → production migrate/deploy → smoke → evidence`

每一步失败都阻止相应的完成标签。重跑失败项后可继续；涉及基础模块更改时重跑受影响的关键路径。发布过程记录 git SHA、锁文件、数据库迁移版本和不可变镜像；不能仅以 `latest` 作为回滚依据。

生产开关至少包括：暂停新任务、暂停新 Checkout、禁用某供应商、降低执行并发、关闭非核心功能。保留查账、取消和恢复路径，避免全站关闭使已付费用户无法查看结果。

## 8 最终交付包

交付给用户的内容应可以独立理解：

1. 在线地址、产品实现了什么，以及一次完整使用路径。
2. 管理员入口和授权方式；密钥用凭据系统交接，不写进报告或仓库。
3. 源代码位置、模板版本、git SHA、Web deployment id、worker 镜像 digest。
4. 具体支付模式和 live 验证状态；订单、权益、结果的验收引用。
5. 已测容量及负载定义，重任务的并发和排队限制。
6. 托管资源归属、预算、告警接收人、支持入口、续费与停机方式。
7. 回滚、备份恢复与任务/支付故障处理步骤。
8. 尚未验证或明确未实现的事项。

状态使用 `preview`、`production_unverified`、`production_verified`，避免把“可打开”和“付费闭环已验证”混淆。每次复制 evidence 模板，所有验收从 `not_run` 开始，不沿用上一个产品的通过记录。

## 9 示例产品的最小闭环

“做一个输入网站 URL、生成竞品摘要、可以付费下载的工具”可收敛为：用户输入 URL → 看输出示例和价格 → 登录 → 支付一份报告 → webhook 确认 → 入队 → 查看生成进度 → 获得并下载报告 → 后台查订单和失败任务。自动退款或人工处理的触发条件要事先写明。

这个版本不需要聊天 agent、长期记忆、团队席位或浏览器账号池。只有当可靠数据源、任务成本和付费意愿得到验证后，再决定扩展订阅或更多数据渠道。
